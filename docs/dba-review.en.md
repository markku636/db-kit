# DBA review guide

[繁體中文](./dba-review.md) · **English**

Hand SQL or a table structure to one (or several) **DBA personas** for review. The DBA doesn't just look at what you attach: while connected, it calls read-only database tools on its own (`EXPLAIN` for the actual plan, columns and indexes, row counts) and verifies before reaching a conclusion. Every tool call is listed in the result.

The first line of the reply is always the verdict:

| Verdict | Meaning |
|---|---|
| `GO` | Safe to run as written |
| `CAUTION` | Can be run, but review the risks first |
| `STOP` | Should not be run as is |

---

## Three entry points

| Entry point | What is reviewed | Default persona |
|---|---|---|
| Query tab → More → "DBA review", or the "Review" tab below | The selected SQL (the whole editor content if nothing is selected), together with rule-engine findings, the structures and indexes of the related tables, and any execution plans already run | Regular connections: Senior DBA; production: Production gatekeeper |
| Right side of the "Review & Run" dialog | The script to run, the per-statement analysis, target table structures and estimated row counts (the same prompt as `dbk run`) | Same as above |
| Right-click a table in the sidebar → Ask AI → "DBA review of structure…" | DDL, columns, indexes, foreign keys, row count and size | Same as above |

---

## Using the panel

- **Choosing personas**: Click a persona chip to toggle it. **Selecting several makes it a panel review**: the same content is given to all of them to review in parallel (up to 4 at a time, the rest are queued), each in its own tab, and the "Combined" verdict at the top takes the strictest one (STOP > CAUTION > GO; a reviewer that gave no verdict counts as CAUTION). The "Panel review" button applies the default lineup from settings.
- **What the DBA checked**: Above each reviewer's result is a "Tool calls" list showing every query it actually ran, how many rows came back and how long it took.
- **Applying fixes**: SQL blocks in the reply have "Apply to editor (diff preview)", which uses the same diff view as the editor's AI actions: each hunk can be rejected or edited by hand, and accepted changes go into the undo history. You can also "Open in query tab" or copy.
- **Follow up in the assistant**: Carries the review task and result into the assistant conversation on the right, so you can go on to ask "Why would this lock the table?".
- **Edit this prompt**: Before sending, view and modify the full prompt (persona + task) for this one run. It applies only this time and doesn't change the library.
- **Adjusting personas and templates**: The library button on the panel opens the AI library directly (see the [AI library guide](./ai-library.en.md)).

## Which tools reviewers can use

| Situation | Available tools |
|---|---|
| Persona has `dbkit-db-tools: false` | No database queries (one-shot review) |
| No connection | No database queries |
| Persona has a `tools:` list | Only the tools in the list (e.g. the gatekeeper can only look at structures and plans) |
| Review & Run, with "Before-image samples sent to AI" set to 0 | Only `list_databases` / `list_tables` / `describe_table` / `explain_query`: **no tools that would fetch actual data are given**, consistent with "by default no data is sent" |
| Otherwise | All read-only tools (200 rows / 8 KB / 30 seconds limit; writes are impossible by design) |

The number of turns is determined by the persona's `maxTurns` (default 10). When the budget runs out, the DBA is asked to reach a conclusion directly from the data it has already gathered, so the review isn't thrown away. API providers don't save DBA reviews as db-kit conversation history (fetched data is not persisted to disk); Claude Code / Codex CLI save sessions according to their own settings.

All four AI providers are supported: for API providers, db-kit runs a built-in tool loop; Claude Code uses `--allowedTools` to allow only dbkit tools and `--max-turns` to cap the turns; for Codex, `dbk mcp --tools` restricts the tools on the server side.

## Command line

The AI review in `dbk run` also uses DBA personas:

```bash
# By default, the persona is chosen based on whether the connection is production
dbk --conn prod-mysql -d shop run migrate.sql --out D:/db-backups --review-cmd "claude -p"

# Specify personas; comma-separated multiple = panel review, verdict takes the strictest (on STOP, only the backup is generated by default)
dbk --conn prod-mysql -d shop run migrate.sql --out D:/db-backups --review-cmd "claude -p" --persona dba-prod-gatekeeper,dba-security

# See the actual prompt sent to the external command (persona + task; the external command only receives stdin)
dbk --conn prod-mysql -d shop run migrate.sql --out D:/db-backups --print-prompt --persona dba-senior
```

## Making it your team's DBA

1. AI library → Personas → pick a built-in DBA → "Copy as custom" (same name = override, new name = save as a separate one).
2. Write your verdict thresholds in the body, and check `team-conventions` under "Preloaded skills" (copy it first and write your team conventions into it).
3. To share with the whole team: move the personal-layer files into a git repo, and have everyone add that team folder under "Sources & sync"; in CI, run `dbk ai lint --dir .`.
4. To use the same DBA in Claude Code too: "Sync to Claude Code / Codex".
